1设计原则与约束

所有技术决策从这 5 条原则推导；与 PRD 的 8 项决议一一对应。

1.1 设计原则

原则含义与推导
① 零运维优先部署在村委会办公电脑，无专职运维、无 DBA。选型上排除一切需要独立服务进程的组件（独立数据库、独立检索引擎），全部能力收敛进一个 Python 进程 + 一个数据库文件。
② 单机可跑一台普通办公电脑（4GB 内存级别）承载全部功能；断网时除问答生成外其余功能全部可用（登录、知识库管理、记录查询均为本地能力）。
③ 防幻觉优先"无来源不构成答案"是产品底线（PRD 6.1），技术上有三道闸门：提示词约束 → 结构化输出 → 服务端引用校验（见 5.3）。引用四要素由服务端从数据库读取组装，不信任模型输出。
④ 服务商可替换大模型走 OpenAI 兼容协议（PRD 决议③：API 接入、服务商实施期定）。换服务商只改配置文件中的 base_url / api_key / model 三项，不改代码。
⑤ 失败不落库问答记录只在"生成成功且校验通过"后单事务写入（PRD 6.5），任何中间失败都不产生半成品记录，不污染留痕与未答清单。

1.2 已确认的技术约束（承接 PRD）

约束技术含义
单村试点，账号 20–50 人并发极低（工作时段同时提问 ≤ 5 人）；数据量单村量级；无需考虑水平扩展
村委会办公电脑、常规网络Windows 10/11 环境；无固定公网 IP、无域名、无 HTTPS 证书 → 局域网内 HTTP 访问 + 服务端 Session
大模型 API 接入云端唯一外部依赖；问答内容经 API 出域 → 敏感拦截必须在本地、先于任何 API 调用执行
企业知识库级系统、轻量务实功能上对齐知识库管理（状态机/留痕/聚合），工程上按"单进程 + 嵌入式存储"实现，不引入分布式组件
问答记录保留 1 年、不可删SQLite 表仅提供 INSERT 路径；到期数据以"提示导出归档"处理（细则 TBD）
自建账号体系Session + bcrypt + 登录锁定，全部本地实现，不依赖任何身份服务

2.3 关键架构决策记录（ADR 摘要）

#决策理由被否方案
ADR-1同步等待 LLM 返回，不做 SSE / WebSocket / 轮询生成耗时 2–8s，一次 HTTP 请求等待（客户端超时 30s）即可；少一套任务队列与状态机，故障面小异步任务 + 轮询（复杂度不匹配单村量级）
ADR-2敏感拦截为管线第一步，本地正则执行，先于一切 API 调用敏感内容不得出域（合规强约束），且省 API 调用；本地执行无网络依赖交给 LLM 判断（内容已出域，且不可控）
ADR-3引用四要素由服务端从数据库组装，LLM 只产出"答案正文 + 引用条目 ID"来源信息（文件名/单位/时间）是信任核心，不能让模型复述（可能改写、编造）让 LLM 输出完整引用卡片（存在幻觉改写风险）
ADR-4查询层双保险过滤条目状态（status=published 且 expire_date 未到），到期下线定时任务仅做状态标记即使定时任务漏跑，过期内容也不会被检索引用——防幻觉底线不依赖单一定时器仅靠定时任务下线（有时效风险）
ADR-5不引入 LangChain / LlamaIndex 等编排框架本场景管线只有 6 步、无 Agent/工具调用/多轮规划需求，httpx 直连 200 行内解决；框架引入版本动荡与调试黑盒LangChain（抽象层收益 < 维护成本）
ADR-6Docker 不作为首选交付方式办公电脑多为 Windows 家庭版（无 Hyper-V），且村委会无人维护容器；NSSM 原生服务 + venv 更贴合现实Docker Desktop（环境门槛高）

3技术栈选型

总原则：成熟稳定、零运维、可替换。每一层给出选型、理由与被否备选。

3.1 选型总表

分层选型选型理由备选方案与不选原因
语言 / 运行时 Python 3.12+ LLM / 检索 / NLP 生态最全（httpx、jieba、bcrypt 均一行安装）；开发效率高，适合村级项目的单人可维护性 Node.js（生态够用但中文分词与本地检索生态弱）；Go（运维友好但开发慢，LLM 生态不成熟）
Web 框架 FastAPI + Uvicorn 原生 async——问答请求要等待外部 LLM API 数秒，异步不阻塞其他用户；Pydantic 自带请求校验与 OpenAPI 文档；社区活跃、文档完善 Flask（同步模型下 LLM 等待会占满 worker）；Django（自带 Admin/ORM 但体量与学习成本超出本项目需要）
模板 / 前端 Jinja2 服务端渲染 + 原生 JS / CSS（无构建步骤） 20–50 名用户的管理台无需 SPA；无 node_modules / 无打包链，办公电脑上改一行页面即生效；表单校验、列表筛选用原生 JS 足够 Vue / React SPA（需 Node 构建工具链，交付与维护成本翻倍，对 5 个页面的系统得不偿失）
数据库 SQLite（WAL 模式）+ SQLAlchemy 2.x 零安装、零守护进程、单文件即完整备份；本场景写少读多、并发 ≤5，WAL 模式完全胜任；SQLAlchemy 统一数据访问并为将来换库留门 MySQL / PostgreSQL（需安装并维护独立服务，违背零运维原则；单村量级用不到其网络并发能力）
关键词检索 SQLite FTS5 + jieba 分词 FTS5 是 SQLite 内建虚拟表，零额外组件；jieba 纯 Python 实现中文分词，入库与查询共用同一分词器保证一致 Elasticsearch（JVM 常驻内存 1GB+，办公电脑吃不消）；Like 模糊查询（无分词能力，召回差）
向量检索 sqlite-vec（SQLite 向量扩展） 与业务库同文件、同进程，条目发布与向量更新在一个事务里；百级条目暴力扫描毫秒级返回；不引入独立向量库 Chroma（可接受但多一套存储文件）；FAISS（无元数据管理，偏研究用途）；pgvector（连带引入 PostgreSQL）
Embedding 大模型 API 的 embeddings 接口（OpenAI 兼容） 与生成模型同协议，httpx 客户端复用；问题与条目共用同一 embedding 模型保证相似度可比较 本地 bge/m3e 模型（免 API 费用但需 CPU 推理与模型下载，办公电脑负载与维护成本高；列为备选降级方案）
大模型（生成） OpenAI 兼容协议的国内合规大模型 API（候选：智谱 GLM / 通义千问 / DeepSeek 等，实施期完成合规评估与数据协议后确定） OpenAI 兼容已是事实标准：换服务商只改 .env 三个字段；国内头部厂商均已完成生成式算法备案，满足"合规服务商"约束 本地开源模型（违背"API 接入"决议且办公电脑无 GPU）；直接绑死单一厂商 SDK（失去可替换性）
LLM 客户端 httpx（异步）直连 OpenAI 兼容协议就是普通 REST，超时/重试/降级逻辑自己写 200 行，完全可控、可调试 LangChain / LlamaIndex（见 ADR-5）；openai 官方 SDK（可用，但对"部分兼容"的国内网关偶有版本坑，httpx 最稳）
认证 / 会话 服务端 Session 表 + HttpOnly Cookie（SameSite=Lax）+ bcrypt 自建账号（决议⑧）+ 单机 Web 场景，Session 是最简模型；bcrypt 是密码哈希事实标准；服务端会话可主动失效（锁定/停用即时生效） JWT（无状态令牌无法即时吊销，锁定/停用语义麻烦，对本场景是负资产）
定时任务 APScheduler（进程内） 与服务同进程同数据库，不存在"任务跑着服务停了"的状态不同步；四行代码注册任务 Windows 任务计划 + 独立脚本（多一套部署物，与服务状态脱节）
进程常驻 NSSM 注册 Windows 服务 开机自启、崩溃自动重启、以服务方式运行不依赖登录会话；村委会"重启电脑系统自己回来" 计划任务启动（重启策略弱）；Docker（见 ADR-6）
配置管理 pydantic-settings + .env 文件 API 密钥与阈值参数（相关性/聚合/超时）集中一处、类型校验、改动重启即生效 配置写死代码（改阈值要发版）；数据库配置表（改动即时但密钥入库不安全）
备份 Python 脚本（sqlite3 backup API）+ Windows 任务计划每日复制 SQLite 官方在线备份接口保证副本一致性（比直接复制文件可靠）；保留 30 天滚动 仅人工拷贝（依赖自觉，不可靠）
日志 标准库 logging + 按大小滚动 应用日志 / 访问日志落文件，磁盘自保护 ELK 等（体量完全不匹配）

3.2 技术栈全景一览（一图速览）

Python 3.12→ FastAPI + Uvicorn→ Jinja2 + 原生 JS→ SQLAlchemy + SQLite(WAL)→ FTS5 + jieba+ sqlite-vec→ 大模型 API（OpenAI 兼容）→ APScheduler→ NSSM 常驻
全部组件均为 pip 可安装的开源组件（NSSM 为单 exe 绿色工具），无商用授权费用；唯一按量付费项为大模型 API 调用（费用与提问量线性相关，量级可控）。

4.7 sessions 会话表 与 内置数据表

  • sessions：session_id（32B 随机）· user_id FK · expires_at（7 天滑动续期）· created_at。登出即删行；停用/锁定即时生效（每次请求校验用户状态）。
  • sensitive_rules 敏感规则（P0 内置 4 类，存表便于留痕展示，P1 开放维护的伏笔）：name（涉法涉诉/医疗诊断/信访举报/涉资金个人决策）· patterns（正则 JSON 数组）· advice（建议渠道文案）。
  • referral_map 转办映射：category → 建议部门 + 文案（实施期由管理方确认，见 PRD 6.2 TBD）。以初始化数据形式插入，改表不发版。

5核心流程设计

问答管线是系统心脏：一次提问最多经历 6 个环节，任何环节失败都有明确出口，不留半成品。

5.1 问答管线总览（FR-01）

① 提交校验→ ② 敏感拦截（本地）命中→ 拦截卡片 + 落库"超出范围"
②放行→ ③ 混合检索（FTS5 + 向量）→ ④ 相关性判定高相关→ ⑤ Prompt 组装 → ⑥ LLM 生成 → ⑦ 引用校验
④不足→ 兜底卡片（相关条目≤3 + 转办建议）→ 落库"未命中" → 未答问题聚合 · ⑦通过→答案卡片 + 落库"已回答" · ⑦失败/⑥超时 → 重试按钮，不落库

交互演示（技术管线步进模拟）

demo-T1 · 问答管线步进模拟器：命中 / 未命中 / 敏感拦截 三条路径逐环节走一遍
⚠ 演示环境：检索分数、相似度、模型输出均为虚构示例，用于评审管线设计，不代表真实参数。
选择场景后点击"开始"，逐环节查看每一步的输入 / 判定 / 输出

5.2 各环节技术规则

① 提交与校验

  • 服务端复验：非空、去首尾空白、≤500 字（前端 maxlength + 后端双保险）；未登录 401；被锁定/停用 403。
  • 知识库为空（无已发布条目）：跳过③④⑤⑥⑦，直达未命中兜底（PRD：空态提问照常受理，未答照常记录）。

② 敏感拦截（本地，先于一切 API 调用 —— ADR-2）

  • 加载 sensitive_rules 全部正则（4 类 × 若干关键词，内存缓存，规则变更时刷新）；正则逐条匹配问题文本。
  • 命中 → 组装拦截卡片（类别对应建议渠道 + "不构成专业意见"提示）→ 单事务落库 status='out_of_scope'（记录命中类别）→ 不生成未答问题 → 流程结束。问题文本不出域。

③ 混合检索

  • 双路召回：FTS5 关键词检索（问题 jieba 分词 → MATCH 查询）+ 语义检索（问题 embedding → sqlite-vec 与已发布条目向量算余弦相似度）。
  • RRF 融合（k=60）合并两路结果取 Top 5；embedding API 调用失败 → 降级为纯关键词召回，记录标 degraded=1。
  • 候选集恒为"已发布且未过期"条目（ADR-4）；草稿 / 已下线 / 已过期条目物理上仍在索引中，但被查询条件排除——下线即时生效，无缓存一致性问题。

④ 相关性判定

  • Top 1 向量相似度 ≥ 阈值 T1（初始 0.75，.env 可调），或 FTS 明确命中（标题/标签强匹配）→ 判定"高相关"进入生成；否则走未命中兜底。
  • 无候选 / 全部低分 → 未命中。"依据不足"属于正常业务结果，照常落库（区别于技术失败，见 5.4）。

⑤ Prompt 组装 + ⑥ LLM 生成

  • 组装模板见 5.3；httpx 异步调用，connect 5s / read 30s 超时，5xx/网络错误自动重试 1 次（退避 2s）。
  • 要求 JSON 输出（服务商支持 response_format=json_object 则启用，否则提示词约束 + 解析容错）。

⑦ 引用校验（防幻觉闸门）

  • 校验 1：模型返回的 cited_ids ⊆ 本次提供的条目 ID 集合，否则视为生成失败。
  • 校验 2：sufficient=false 或答案为空 → 转未命中兜底（模型自认依据不足，尊重其判断）。
  • 组装 3（ADR-3）：答案卡片四要素由服务端按 cited_ids 从 kb_entries 读取；时效提示行由 last_verified_at 组装。模型输出的正文以外内容一律丢弃。

⑧ 落库与返回

  • 生成成功且校验通过 → 单事务写入 qa_records（status='answered', answer, cited_entry_ids）→ 返回答案卡片。
  • 未命中 → 单事务写入 status='missed' + 同事务生成 unanswered_item 并聚合（见 5.5）→ 返回兜底卡片。
  • 敏感 → 落库 status='out_of_scope' → 返回拦截卡片。

5.3 Prompt 模板与结构化输出

# System（要点摘录）
你是村务政策问答助手，服务基层工作人员。
规则：
1. 仅依据 <知识条目> 提供的内容作答，禁止使用条目以外的知识；
2. 条目内容不足以可靠回答时，必须将 sufficient 置为 false，并停止作答；
3. 答案分点、直接回应问题、口径供工作人员向村民复述；
4. 只输出 JSON：{"answer": "...", "cited_ids": [条目id...], "sufficient": true|false}

# User（组装后）
问题：{question}
<知识条目 id=12>
标题：最低生活保障申请指南
正文：{条目正文}
</知识条目>
（…Top 3 条目，第 4-5 名低相关条目丢弃不送，减少干扰）

# 期望输出（服务端解析）
{"answer":"申请低保一般需准备：① 书面申请书…","cited_ids":[12],"sufficient":true}
防幻觉三道闸：① 提示词硬约束"仅依据条目"；② 结构化 JSON 便于机器校验；③ 服务端校验引用 ID 合法性并以数据库组装四要素。三道闸任何一道不通过，都不产生"已回答"记录。

5.4 失败语义区分（PRD 6.5 的技术落地）

情形性质处理是否落库
依据不足 / 无高相关条目业务结果走未命中兜底，进入未答清单是（missed）
敏感命中业务结果拦截卡片 + 建议渠道是（out_of_scope）
LLM 超时 / 5xx / 解析失败 / 引用 ID 非法技术失败自动重试 1 次 → 仍失败返回"生成失败，请重试"（HTTP 503, retryable）否——重试成功才落库，无半成品
embedding 失败技术降级自动降级纯关键词检索继续作答，记录标 degraded是（标 degraded=1）

5.5 未答问题聚合与手动拆分（FR-04）

聚合算法（单村量级从简，可解释优先）

  1. 未命中落库同事务内：计算问题 embedding，生成 unanswered_item；
  2. 遍历所有 status='pending' 的组：新问题向量与组内全部 item 向量求平均余弦相似度；
  3. 最大平均相似度 ≥ 阈值 T2（初始 0.82） → 并入该组（question_count+1，last_asked_at 刷新）；否则新建组（代表问题 = 该问题，count=1）；
  4. 关闭/已补充的组不再参与聚合（闭环后的相似新问题会生成新组，符合"补充后再问直接命中"预期）。

手动拆分

  • 组详情页展示全部成员问题；管理员勾选误聚合的问题 → 确认拆分 → 选中 items 移入新组（代表问题取首个，各自独立计数），原组 count 相应减少；
  • 拆分、并入均写 operation_logs（action=unanswered_split）留痕。

发布闭环（自动双向关联）

  • 管理员从组点"去补充"→ 跳转新增条目表单（带入组 ID 与问题作参考）；
  • 该条目发布事务内：回查来源组 → 组 status='supplemented'，related_entry_id=新条目 ID（双向关联完成）——不依赖额外定时任务，发布即闭环。

5.6 条目状态机与到期自动下线（FR-03）

draft 草稿—发布→ published 已发布—手动下线(原因必填)→ offline 已下线—重新发布→ published
published—定时任务: expire_date ≤ 今日→ expired 已过期—编辑更新后重新发布→ published
  • 编辑不改状态：published 条目保存后仍 published，刷新 last_verified_at，写留痕（kb_edit）。
  • 到期下线：APScheduler 每小时扫描 status='published' AND expire_date ≤ 今日 → 置 expired + 留痕；双保险：检索查询条件独立过滤过期条目（ADR-4），定时器漏跑零影响。
  • 标题唯一：DB UNIQUE 约束兜底；新增/编辑保存时对标题做 embedding 与已发布条目标题比对，相似度 ≥ T3（初始 0.85）→ 前端提示"是否为原条目的更新版本"，引导编辑原条目。
  • 即时生效：发布/下线事务内同步更新 FTS 与向量表，无缓存层，发布后下一次提问即生效。

5.7 定时任务清单（APScheduler）

任务频率动作对应需求
条目到期下线每小时 :00published 且过期 → expired + 留痕FR-03 规则 5
数据库备份每日 03:00WAL checkpoint → sqlite3 backup API 复制 → 备份目录滚动保留 30 份运维（8.2）
会话清理每日 02:00删除过期 sessions安全
记录保留检查每日 02:30扫描超 1 年记录 → 管理端提示"可导出归档"（P0 只提示不删除，处置细则 TBD）6.4

6接口设计概要

页面（Jinja2 渲染）+ JSON API 两类。写操作均为 POST/PUT + Session 认证，无公开匿名接口。

6.1 页面路由（GET，未登录一律跳 /login）

路径说明权限
/login · /change-password登录、首次/强制改密（must_change_password=1 时其余页面全部拦截）匿名 / 登录
/问答工作台（提问、答案卡片、反馈、我的记录侧栏）工作人员 + 管理员
/records我的问答记录（倒序、状态筛选、详情）本人记录
/admin/kb知识库管理（状态筛选、新增/编辑抽屉、发布/下线、留痕）管理员
/admin/unanswered未答问题（组列表、详情/拆分、关闭）管理员
/admin/accounts · /admin/logs账号管理、操作留痕查询管理员

6.2 JSON API 概要

方法 + 路径入参 → 出参（要点）权限
POST /api/ask{question} → ①answered：answer + cited(四要素) + 时效行　②missed：兜底（相关条目≤3 + 转办建议）　③out_of_scope：建议渠道　④503 retryable：生成失败（不落库）登录
POST /api/records/{id}/feedback{useful|useless} → 200；非本人/非 answered → 403/409本人
GET /api/kb?status=条目列表（分页/筛选）管理员
POST /api/kb · PUT /api/kb/{id}新增（草稿）/ 编辑；必填校验、标题唯一、相似提示标志返回管理员
POST /api/kb/{id}/publish发布：校验必填 → 状态流转 → 更新索引 → 关联未答组闭环 → 留痕管理员
POST /api/kb/{id}/offline{reason 必填} → offline + 留痕管理员
GET /api/unanswered/groups?status=组列表（代表问题、count、状态、关联条目）管理员
POST /api/unanswered/groups/{id}/split{item_ids[]} → 拆出新组，双方计数更新 + 留痕管理员

7安全与合规设计

自建账号体系的全部安全责任在本机；大模型 API 是唯一出域通道，边界必须清晰。

7.1 认证与会话

项设计对应需求
密码存储bcrypt cost=12；初始密码 secrets 模块生成 12 位（大小写+数字），创建响应展示一次，管理员线下转交FR-05 规则 2
首次登录强制改密must_change_password=1 → 中间件放行仅 /change-password，其余一律 302FR-05 规则 2
登录锁定失败 +1；≥5 次 → locked_until=now+15min，期间拒绝并提示剩余时间；成功清零。阈值 .env 可调FR-05 规则 3
会话服务端 session 表 + HttpOnly/SameSite=Lax Cookie（7 天滑动）；登出删行；每请求校验账号状态 → 停用/锁定即时生效FR-05 规则 4
CSRFSameSite=Lax + 写操作全部 POST/PUT + 关键表单携带一次性 token—
XSSJinja2 自动转义所有插值；答案正文按"纯文本 + 换行/分点"渲染，不做富文本 HTML 透传—

7.2 数据边界与个人信息保护（PRD 7.2）

  • 出域内容最小化：LLM 请求只包含"问题文本 + 已发布条目内容"，不含提问人身份、账号、IP；问题文本本身在敏感拦截之后才可能出域。
  • 敏感拦截前置（ADR-2）：4 类敏感内容本地正则拦截，不调用 API、不出域。
  • 界面明示：输入框常驻提示"请勿输入村民姓名、身份证号等个人敏感信息"（PRD 合规要求）。
  • 记录可见性：qa_records 仅本人与管理员可查（4.2 权限矩阵）；导出能力 P1，P0 不提供批量导出入口。
  • 留痕不可篡改：operation_logs append-only + 触发器禁改禁删（4.6）。

7.3 大模型 API 合规（承接 PRD 约束）

  • 服务商准入（实施期完成）：已完成生成式 AI 服务备案；签署数据协议（明确：不得用于模型训练、保留期限、处置方式）；协议条款确认前不接入生产数据 TBD。
  • API 密钥保管：仅存 .env（gitignore、不进代码库、不入每日备份明文——备份脚本排除该文件，密钥单独封存登记）；泄漏应对：服务商控制台立即轮换 + 更新 .env 重启。
  • 可替换：OpenAI 兼容协议 + 生成/嵌入服务商均只以 .env 三字段（base_url/api_key/model）配置；换服务商流程：改配置 → 重启 → 跑向量重建脚本（4.3 note）→ 抽样验证 10 问。

7.4 网络边界

  • 服务仅监听村内办公网段网卡（或 localhost），Windows 防火墙仅放行同网段入站 部署建议；无公网暴露、无端口映射。
  • 机器锁屏策略沿用办公电脑现有管理要求（系统外，运维手册说明）。

8部署与备份

目标：村干部"重启电脑后系统自动回来"，备份恢复一个文件搞定。

8.1 环境要求

项要求
硬件村委会办公电脑：Windows 10/11（64 位）、内存 ≥4GB、磁盘剩余 ≥2GB
软件Python 3.12+（安装时勾选 pip）、NSSM（单 exe）、Chrome/Edge 浏览器
网络常规网络：村内访问走局域网；出网仅需 HTTPS 访问大模型 API 域名

8.2 安装步骤（一次性，约 6 步）

  1. 安装 Python 3.12（勾选 Add to PATH）；
  2. 解压发行包到 D:\vqa-system\，python -m venv venv + pip install -r requirements.txt（离线环境用随包 wheel 目录安装）；
  3. 复制 .env.example → .env，填入大模型 base_url / api_key / model 与阈值参数；
  4. python manage.py init-db：建表 + 插入内置敏感规则与转办映射 + 创建首个管理员（打印初始密码，抄录后交村委会）；
  5. NSSM 注册服务：启动 Uvicorn，配置开机自启 + 崩溃自动重启；
  6. 浏览器验证：登录 → 改密 → 录入 3 条示例条目 → 发布 → 试问一轮。

8.3 备份与恢复

项方案
自动备份每日 03:00（APScheduler）：WAL checkpoint → sqlite3 backup API 复制 app.db → backup\yyyy-mm-dd.db，滚动保留 30 天
离机备份 建议每周拷贝最近一份备份到 U 盘/村委会另一台电脑（防整机故障/失窃）
恢复停服务 → 用备份文件覆盖 app.db → 起服务；RPO ≤ 24h（每日一次）
恢复演练 建议上线后演练一次"备份文件 → 新机器 30 分钟拉起"，写入运维手册

8.4 升级与变更

  • 升级流程：停服务 → 手动备份 → 替换代码 → manage.py migrate（建表差异脚本，初期 create_all + 手工 ALTER，量级增长后再评估 Alembic）→ 起服务；
  • 换大模型服务商：改 .env 三字段 → 重启 → 运行向量重建脚本（条目与未答问题 embedding 全量重算，百级条目 < 1 分钟）→ 抽样验证；
  • 密钥轮换：服务商控制台生成新 key → 改 .env → 重启（旧 key 作废）。

9故障与降级

每类故障都有明确的系统行为；本地能力与大模型依赖的故障域严格分离。

故障场景影响面系统行为恢复路径
大模型 API 超时/故障仅"答案生成"不可用自动重试 1 次 → 仍失败提示"生成失败，请重试"；不落库；知识库/记录/账号等本地功能全部正常服务商恢复；或切换备用 .env 配置重启
embedding 接口故障语义检索降级自动降级纯关键词检索继续作答，记录标 degraded=1；聚合暂停（新未答问题各自成组，API 恢复后由管理员视情合并）API 恢复自动结束降级
整机断网问答生成不可用登录、知识库管理、记录查询、未答处理全部可用（本地）；敏感拦截照常网络恢复
进程崩溃服务瞬断NSSM 自动重启（秒级）；崩溃前未落库的提问无残留（单事务）—
数据库文件损坏数据风险停服务 → 取最近每日备份恢复，RPO ≤ 24h备份恢复（8.3）
定时任务漏跑过期条目未及时标记检索层双保险过滤（ADR-4），问答不受任何影响；状态由下个周期补齐自动
API 密钥泄漏安全风险服务商控制台轮换 + 改 .env 重启（7.3）流程写入运维手册
磁盘写满服务异常日志按大小滚动 + 备份滚动 30 份，常态占用 <1GB；运维手册提供磁盘检查项人工清理
